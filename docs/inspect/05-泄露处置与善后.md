# 05 · 泄露处置与善后

> 清理 Git 历史只能解决“现在还能从仓库访问”的问题，不能假设数据从未被别人看到。本文按“已泄露”处理，给出处置清单。

## 二、立即处置（建议当天完成）

### 2.1 仓库转 Private

GitHub → `Settings` → `General` → `Danger Zone` → `Change repository visibility` → **Private**。

- 目的：立即停止公开访问。
- 可逆：清理完成、确认无敏感内容后可再改回 public。
- 注意：转 Private 不会删除已经存在的 fork、缓存或别人本地的 clone。

### 2.2 重置受影响账号密码

见 `04-清理执行手册-PowerShell.md` 阶段 1.2。核心：

- 对两个受影响账号重置密码。
- 使用 `src.security.hash_password` 生成新哈希，不要写明文。
- 如果账号不再需要，停用/删除。

### 2.3 吊销旧会话

```sql
UPDATE auth_sessions
SET revoked_at = strftime('%Y-%m-%dT%H:%M:%fZ', 'now')
WHERE revoked_at IS NULL;
```

或按用户吊销。这样泄露期间签发的 bearer token 立即失效。

### 2.4 通知受影响用户

告知：

- 哪些数据可能暴露（用户名、显示名、聊天内容、密码哈希）。
- 建议更换密码；如果他们在其他网站复用了同一密码，也应更换。
- 不要恐慌：密码是 scrypt 哈希，不是明文；但聊天内容是明文。
- 如果这是课程项目，告知指导老师/团队成员，保留处置记录。

### 2.5 检查 GitHub 上是否还有副本

- **Forks**：`https://github.com/seven060413/Smart-Q-A-System/forks`。审查时为 0。
- **Releases**：审查时为空。
- **Issues/PR**：仓库有 1 个 open issue；检查正文/评论/附件是否贴过 SQL、日志、服务器信息。
- **Actions artifacts**：审查时没有工作流；如有，删除含敏感日志的 run/artifact。
- **Pages**：Settings → Pages；如果启用，旧构建可能仍可访问，禁用或重建。
- **Wiki/Discussions**：检查是否有人粘贴过数据。

### 2.6 联系 GitHub Support 清理缓存

Force push 后，旧提交可能短期仍可通过 SHA 访问。按 GitHub 官方流程联系 Support：

```text
https://support.github.com/contact
```

提供仓库 URL、旧提交 SHA、已移除的路径，并说明已用 `git filter-repo` 重写历史。请求清除缓存视图/旧对象。

参考：

```text
https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository
```

## 三、服务器侧安全检查（建议）

虽然这次泄露的是 GitHub 上的数据导出，不是服务器被入侵，但部署文档公开了服务器 IP 和 root 登录方式，建议顺手检查：

1. **SSH**
   - 是否允许 root 密码登录？建议改为密钥登录，禁用 `PasswordAuthentication`。
   - 是否限制了来源 IP？至少确认没有把 root 密码写在任何文档里。
   - 检查 `/var/log/auth.log` 或 `journalctl -u ssh` 是否有异常登录尝试。
2. **安全组**
   - 后端 `18080` 是否仍对 `0.0.0.0/0` 开放？按 `docs/HTTPS部署指南.md` 的建议，应只允许 `127.0.0.1`，由 Nginx 反代。
   - 只开放 80/443（以及必要的 SSH 来源）。
3. **数据库**
   - `data/app/ikgr.db` 权限是否过宽？建议仅服务账号可读。
   - 备份文件中是否包含敏感数据？备份也应加密/限权。
4. **密钥**
   - `.env` 未进 Git，但确认它没有被复制进任何部署包、截图、聊天记录或网盘。
   - 如果曾经把 `.env` 发给别人/上传网盘，按泄露处理并轮换 DashScope/ASR 密钥。

## 四、长期防复发

### 4.1 `.gitignore` 是底线，不是万能

本次已经提供完整 `.gitignore`（`03-gitignore-proposed.txt`）。但它：

- 只对**未跟踪**文件生效；
- 不能阻止 `git add -f`；
- 不能阻止有人把文件改名后提交；
- 不能阻止历史中已有的泄露。

所以还需要下面的习惯/工具。

### 4.2 不要用 `git add -A` / `git add .`

在包含数据库、导出、日志、部署包的仓库里，`git add -A` 很容易把不该提交的文件带进去。建议：

```powershell
git status
git add <明确列出的文件>
```

提交前看一眼 `git diff --cached --stat`。

### 4.3 可选的 pre-commit hook

在仓库里放一个受版本控制的 hook，例如 `scripts/hooks/pre-commit`：

```sh
#!/bin/sh
# 阻止常见敏感/产物文件进入暂存区
blocked=$(git diff --cached --name-only --diff-filter=ACM | \
  grep -Ei '(^|/)\.env$|(^|/)\.env\.|\.(sql|db|sqlite3?|log|zip|tar\.gz|tgz|7z|rar)$|(^|/)tar$|migration_data|fix_user_id')

if [ -n "$blocked" ]; then
  echo "❌ 拒绝提交以下敏感/产物文件："
  echo "$blocked"
  echo "如果确实要提交，请使用 git add -f 并在团队内说明。"
  exit 1
fi
```

启用：

```powershell
git config core.hooksPath scripts/hooks
```

> 注意：hook 会阻止所有 `.sql`，包括未来合法的 schema SQL。需要时在 hook 中加白名单，例如 `!db/schema.sql`。

### 4.4 GitHub 侧防护

- Public 仓库默认开启 secret scanning；保持开启。
- 如果仓库转 Private，考虑是否需要 GitHub Advanced Security（付费）或改用本地/CI 扫描。
- 不要关闭 push protection（如果可用）。
- 定期检查 forks、releases、Actions artifacts。

### 4.5 数据导出流程

建议把“导出数据”固定到仓库外目录，例如：

```text
D:\IKGR-private\exports\
D:\IKGR-private\backups\
```

不要放在 `D:\IKGR-system-eands` 里。这样即使误执行 `git add -A`，也不会把导出文件带进仓库。

### 4.6 部署包流程

- 部署包统一输出到 `D:\IKGR-private\deploy\`，不要放仓库根目录。
- 包名带时间戳，例如 `ikgr-deploy-20261115-1430.tar.gz`。
- 打包前排除 `.env`、`data/app/`、`__pycache__`、`.git`。
- 不要把部署包提交到 Git；`.gitignore` 已覆盖 `*.tar.gz`、`*.zip`。

### 4.7 文档脱敏

- 部署文档中的服务器 IP、root 用户、内部路径，建议用 `<服务器公网IP>`、`<user>@<host>` 占位。
- 迁移文档中的真实用户名/姓名/用户 ID，建议改成 `demo_user` / `<user_id>`。
- 课程材料如果需要保留真实信息，放在私有目录，不要放公开仓库。

## 六、一句话总结

**先把仓库转 Private、重置密码，再改写历史；改写历史用独立镜像 + `git reset --mixed` 保住本地文件；force push 后联系 GitHub Support 清缓存；最后用 `.gitignore` + 明确 `git add` 防复发。**
